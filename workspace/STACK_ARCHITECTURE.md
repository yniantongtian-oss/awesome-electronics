# AI-EDA 最终架构

## 目标

把当前仓库集合收敛成一个可以安装、验证、维护和逐步增强的工程系统，而不是继续复制功能重叠的上游仓库。

## 架构决策

### 1. `eda-agent` 是唯一主力 EDA 控制层

原因：

- 同一套包可以选择 `altium`、`kicad` 或 `both` 后端。
- 提供 `health`、`doctor`、仪表盘、离线审查、BOM 和 netlist 等诊断路径。
- 可以把 AI 客户端与具体 EDA 工具隔离，避免客户端直接操作项目文件。
- 已经具备批处理、设计审查、数据表优先和修改后显式保存等安全机制。

边界：

- 不直接复制 `kicad-mcp-1` 或 `KiCAD-MCP-Server` 的代码进来。
- 需要的新能力先以行为测试和接口需求描述，再决定在主力仓库中独立实现。
- 默认后端为 Altium；KiCad 作为同一入口的可选后端。

### 2. `contextgraph` 是独立的代码智能基础层

用途：

- 为修改 `eda-agent`、脚本和测试时提供精确的代码上下文。
- 控制发送给模型的代码量，减少整库读取。
- 后续可作为 MCP 或编辑器集成的基础，但不与 EDA 运行时强耦合。

边界：

- 不放 EDA 业务逻辑。
- 不依赖 Altium、KiCad 或 Windows 专有 API。
- 先保持 Python 项目检索稳定，再扩展 TypeScript/C/C++。

### 3. `KiKit` 只负责制造阶段

用途：

- 拼板。
- Gerber 和装配数据自动导出。
- 多板工程与可重复制造流程。

边界：

- 不参与原理图设计决策。
- 不作为 MCP 主入口。
- 在 PCB 完成 DRC 后才进入工作流。

### 4. `hardware-components` 是外部资产源

用途：

- 查找 KiCad 符号、封装、元数据和三维模型。

边界：

- 不默认完整克隆。
- 不手改流水线生成文件。
- 自己制作的元件应放入单独的小型自有库。

### 5. 两个 KiCad MCP 仓库是评测对象

`kicad-mcp-1` 与 `KiCAD-MCP-Server` 用于：

- 对照工具覆盖。
- 学习测试设计和失败恢复。
- 验证某项需求是否已经有成熟实现。

它们不用于：

- 与 `eda-agent` 同时连接并写入同一个 KiCad 工程。
- 直接互相复制大段实现。
- 默认安装到生产工作区。

## 分阶段落地

### 阶段 A：安装可重复

完成标准：

- PowerShell 脚本能在干净目录中建立虚拟环境。
- `eda-agent` 和 `contextgraph` 可执行文件存在。
- 重复运行脚本不会破坏已有工作区。

### 阶段 B：只读连接

完成标准：

- AI 客户端能调用 MCP。
- 能读取项目、文档、元件、网络和规则。
- 无任何工程文件写入。

### 阶段 C：安全写入

完成标准：

- 在测试工程副本上修改一个非关键文本或元件参数。
- 显式保存并重新打开验证。
- Git diff 或文件备份能确认改动范围。

### 阶段 D：工程审查

完成标准：

- 运行设计快照、lint、ERC/DRC。
- 输出的问题包含位置、对象和可执行修复建议。
- AI 不凭空生成元件参数、封装尺寸或模型。

### 阶段 E：端到端制造

完成标准：

- 从原理图到 PCB 的关键检查通过。
- BOM 可导出。
- Gerber、钻孔、装配文件可生成。
- KiKit 能对已通过 DRC 的板进行拼板。

## 优化优先级

### P0：必须先完成

1. Windows 安装和诊断脚本。
2. 一个固定的测试工程副本。
3. MCP 只读连接验证。
4. 写入前备份与显式保存规则。
5. Altium 和 KiCad 各自的最小验收流程。

### P1：达到稳定可用

1. 统一错误信息与修复建议。
2. 批量操作的事务化或回滚策略。
3. 固定版本依赖和可重现环境。
4. 对 BOM、ERC、DRC、网络和封装的回归测试。
5. GitHub Actions 中的离线测试。

### P2：形成自己的产品

1. 自有元件库和审查规则。
2. 面向中文用户的安装器与界面。
3. 统一 Altium/KiCad 的设计计划格式。
4. 将 `contextgraph` 接入 EDA 代码维护流程。
5. 建立真实 PCB 样板的端到端评测集。

## 不做的事情

- 不为了仓库数量而继续复制同类项目。
- 不在没有数据手册的情况下自动选封装或生成模型。
- 不在用户原始工程上进行首次自动修改。
- 不把超大元件仓库加入普通 CI。
- 不让多个写入型代理并行控制同一个 EDA 会话。

## 最终产品形态

第一阶段的可用产品不是重新写一个大型 EDA，而是：

> 一个能够在 Windows 上稳定安装、连接 Altium/KiCad、读取设计、执行受控修改、完成工程审查并导出制造资料的 AI-EDA 工作区。

等这条链路稳定后，再把高价值功能逐步沉淀到自有代码，而不是先合并所有上游实现。
